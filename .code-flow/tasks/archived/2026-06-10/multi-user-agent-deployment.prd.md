## 2. 背景与目标

### 2.1 问题陈述 [必填]

| 维度 | 内容 |
|------|------|
| **问题描述** | platform-command 当前是单用户本地工具：浏览器会话依赖 kimi-webbridge 操作"用户本人桌面浏览器的活跃 tab"，是隐式全局单例；run 记录、输出路径均无归属概念。无法支撑"服务器部署一套环境、多人共用"的场景——多人共用即共享同一平台身份，操作互相干扰且无法审计。 |
| **当前替代方案** | ① 每人本地各装一套：运维分散、命令库版本不一致、无统一管控。② 单实例 Agent 共享给所有人：Agent 框架（GenericAgent / OpenClaw 均如此）是单租户信任域，用户身份由对话层（LLM）判定，提示注入可跨身份，安全上不成立。 |
| **触发原因** | 团队希望在服务器上部署一套 GenericAgent + platform-command 环境，所有人通过它调用目标平台，且每个人的每次操作相互独立（身份、登录态、数据、记录全部隔离）。 |

### 2.2 目标与价值 [必填]

| 维度 | 内容 |
|------|------|
| **核心目标** | 提供"每用户一容器"的多用户平台操作环境：统一镜像与命令库，按用户隔离身份、登录态、执行记录与输出。 |
| **预期价值** | 一套环境服务全团队，命令库统一维护；用户操作互不可见、互不干扰；执行记录可按人审计。 |

**成功指标**

| 指标 | 当前值 | 目标值 | 衡量方式 |
|------|--------|--------|----------|
| 用户隔离性 | 无隔离（共享单一身份） | 跨用户登录态/数据/记录完全不可见 | 安全验收用例 |
| 新用户开通时长 | 不支持 | 分钟级（脚本化开通） | 开通脚本实测 |
| 命令覆盖 | 仅本地 webbridge 可跑浏览器命令 | API 类与浏览器会话类命令在服务器均可执行 | 两类命令各跑通 ≥1 个真实用例 |
| 日常使用等待 | — | 无容器启动等待（常驻） | 用户发起操作即执行 |

## 3. 用户与场景

### 3.1 目标用户 [必填]

| 维度 | 内容 |
|------|------|
| **用户画像** | ① 业务用户：团队成员，通过 IM（企微/钉钉/TG）或 TUI 向自己的 Agent 实例发指令，执行目标平台操作（查数据、导报表、预演操作等）。规模：起步 ≤10 人，本架构适用上限约几十人。② 管理员：负责镜像构建、命令库维护、用户开通与审计。③ 本地 C 端用户：在自己电脑的 Agent（Claude Code / Codex 等）里安装 platform-command MCP 单机使用，不接触服务器部署，走 webbridge 操作本人浏览器。 |
| **使用场景** | 用户在 IM 里对自己的 Agent 说"导出 XX 平台近 7 天的数据"，Agent 调用 platform-command 以该用户自己的登录态执行命令，结果只回给该用户；同一时间其他用户做同样的事，互不感知。 |

### 3.2 用户故事 [必填]

| 编号 | 用户故事 | 优先级 |
|------|---------|--------|
| US-01 | 作为业务用户，我希望通过自己的入口（IM/TUI）让 Agent 用我自己的登录态执行平台操作，以便结果只归属于我、不与他人混淆 | P0 |
| US-02 | 作为业务用户，我希望能提供和更新我的平台凭证（API token 或浏览器登录态），以便命令能以我的身份执行 | P0 |
| US-03 | 作为管理员，我希望用脚本快速为新用户开通一个隔离环境，以便用户分钟级上手 | P0 |
| US-04 | 作为管理员，我希望命令库统一维护、用户不能注入自己的命令代码，以便控制执行面、避免越权 | P1 |
| US-05 | 作为管理员，我希望每条执行记录都有用户归属，以便按人审计 | P1 |
| US-06 | 作为业务用户，我希望登录态失效时被明确告知并能便捷地重新提供，以便不被静默失败困扰 | P1 |
| US-07 | 作为本地 C 端用户，我希望升级 platform-command 后本地 Agent（MCP stdio + webbridge）的用法和行为完全不变，以便服务器多用户改造不影响我 | P0 |

## 4. 功能需求

### 4.1 功能清单 [必填]

| 功能ID | 功能名称 | 功能描述 | 优先级 | 来源用户故事 |
|--------|---------|---------|--------|-------------|
| FEAT-01 | 基础 Docker 镜像 | 以 Playwright 官方镜像为底，打包 GA（Python 3.12）+ platform-command + headless Chromium + 全局命令库 + 入口脚本 | P0 | US-01, US-03 |
| FEAT-02 | 每用户容器编排与开通 | compose 模板 + 开通脚本：per-user volumes（GA memory、runs/output、登录态）、env 注入 `PLATFORM_COMMAND_USER_ID` 与渠道凭证，容器常驻 | P0 | US-01, US-03 |
| FEAT-03 | Playwright 浏览器适配器 | platform-command `resolveAdapter` 新增 Playwright 路径：headless 环境用用户 storageState 执行 `browser_session_cookie` 类命令，替代 webbridge | P0 | US-01, US-02 |
| FEAT-04 | 登录态接入 | API token 走容器环境变量直连；浏览器登录态由用户本地导出 storageState 后导入容器专属 volume | P0 | US-02 |
| FEAT-05 | 会话过期探测与重登提示 | 命令执行遇 401/403 时标记 session 失效，向用户返回明确的重新提供登录态指引 | P1 | US-06 |
| FEAT-06 | run 记录归属 | run 记录写入 userId 字段，按用户目录隔离，支持管理员汇总审计 | P1 | US-05 |
| FEAT-07 | 输出路径沙箱 | `save_json` 等输出能力的路径收敛到用户专属 output 目录内，拒绝任意绝对路径写入 | P1 | US-01 |
| FEAT-08 | 命令库只读管控 | 全局命令库以只读方式挂载（`/opt/platform-commands`），含 signer 代码在内仅管理员可变更 | P1 | US-04 |
| FEAT-09 | GA 工具约束（软裁剪） | 容器内约束 GA 的浏览器注入/键鼠/屏幕视觉工具（headless 自然失效 + SOP 引导 + 沙箱兜底），平台操作统一经 platform-command CLI 执行 | P1 | US-01 |
| FEAT-10 | 本地模式向后兼容 | 多用户相关改动全部为增量可选：无服务器侧配置时，适配器选择、run 落盘、输出路径、MCP tools 行为与现版本一致 | P0 | US-07 |

#### FEAT-01: 基础 Docker 镜像

- **描述**: 一个预构建镜像承载全部程序与只读内容，所有用户容器共用；数据一律外置 volume。
- **验收标准**:
  - [ ] 镜像内 `platform-command list` 与 GA TUI/IM 前端均可启动
  - [ ] Playwright 版本与 platform-command `optionalDependencies`（^1.52）对齐，headless Chromium 可启动
  - [ ] 镜像内不含任何用户凭证或密钥

#### FEAT-02: 每用户容器编排与开通

- **描述**: 新用户开通 = 起一个新 service + 挂三类 volume + 注入一组 env。
- **验收标准**:
  - [ ] 开通脚本一条命令完成新用户环境创建，分钟级可用
  - [ ] 两个用户容器并行执行同一命令，登录态、run 记录、输出互不可见
  - [ ] userId 仅来自容器环境变量，Agent 对话内容无法变更执行身份

#### FEAT-03: Playwright 浏览器适配器

- **描述**: `capabilities.ts` 的 adapter 选择逻辑新增 Playwright 分支，覆盖 webbridge 四个核心函数的等价能力（带 cookie 的 fetch、会话探测）。
- **验收标准**:
  - [ ] `browser_session_cookie` 类命令在无 webbridge 的容器内用 storageState 成功执行
  - [ ] 本地桌面环境仍优先 webbridge，行为不回归
  - [ ] storageState 缺失/失效时报错信息明确指向 FEAT-04 的导入流程

#### FEAT-04: 登录态接入

- **描述**: 凭证两条通道：token（env）优先，storageState 导入兜底；均落在用户专属 volume，不进镜像。
- **验收标准**:
  - [ ] token 类命令配置 env 后直接可用
  - [ ] 用户按文档导出 storageState 并导入后，浏览器会话类命令可用
  - [ ] 销毁用户环境时登录态 volume 可单独清除

#### FEAT-10: 本地模式向后兼容

- **描述**: 服务器多用户能力以"可选增量"方式实现，本地 C 端用户零感知：不设 `PLATFORM_COMMAND_USER_ID` 等服务器侧环境变量时，一切行为与现版本一致。
- **验收标准**:
  - [ ] 本地环境（无新增 env）下 `browser_session_cookie` 命令仍优先走 webbridge，提示文案不变
  - [ ] run 记录仍落在 cwd 的 `.platform-command/runs/`，无 userId 字段或字段缺省不影响读取
  - [ ] 输出沙箱仅在服务器模式（显式配置）下启用，本地任意路径行为不变
  - [ ] 现有 MCP tools 的入参/出参 schema 不发生破坏性变更，旧版 Agent 配置无需修改
  - [ ] 现有测试套件（`npm test`）全量通过，新增能力以新增用例覆盖

### 4.2 边缘情况 [可选]

| 场景 | 预期行为 |
|------|----------|
| 登录态过期（401/403） | 标记 session 失效，返回重新导入指引，不静默重试 |
| 同一用户并发操作同一平台 | 同一浏览器上下文内串行排队，不交叉污染 |
| 用户诱导 Agent"以他人身份执行" | userId 来自容器 env，对话层无法改变执行身份 |
| 命令输出指定容器外/他人路径 | 拒绝并提示输出沙箱边界 |
| 单个用户容器崩溃 | 仅影响该用户，重启后 volume 数据完整 |
| 本地用户升级新版本（未设任何服务器 env） | 适配器、落盘路径、MCP 行为与升级前一致，零配置迁移 |

## 5. 非功能需求

| 指标ID | 类型 | 要求 |
|--------|------|------|
| NFR-SEC-01 | 安全 | 用户身份绑定在模型不可篡改层（容器环境变量/OS 边界），严禁作为 LLM 可控的工具参数传递 |
| NFR-SEC-02 | 安全 | 登录态独立 volume 存储、可单独销毁；任何凭证不进镜像、不进 git |
| NFR-SEC-03 | 安全 | 用户容器按不可信沙箱配置：命令库只读挂载、出网按需限制、CPU/内存配额 |
| NFR-PERF-01 | 性能 | 容器常驻，用户日常操作无启动等待；新用户开通 ≤ 分钟级 |
| NFR-REL-01 | 可用性 | 单用户容器故障不影响其他用户；volume 数据在容器重建后保留 |
| NFR-COMPAT-01 | 兼容性 | Playwright 基础镜像、platform-command 依赖、浏览器二进制三者版本对齐；GA 需 Python 3.11/3.12 |
| NFR-COMPAT-02 | 兼容性 | 本地单用户模式零破坏：服务器能力全部由显式配置启用，默认路径（webbridge、cwd 落盘、MCP schema）与现版本完全一致 |

## 6. 范围与边界 [必填]

| 类别 | 内容 |
|------|------|
| **范围（In Scope）** | 基础镜像构建；每用户容器编排与开通脚本；platform-command Playwright 适配器；token/storageState 两条登录态通道；run 归属、输出沙箱、命令库只读、GA 工具裁剪；本地单用户模式向后兼容保障 |
| **非范围（Out of Scope）** | 共享浏览器会话 daemon（几十用户、内存吃紧后再做的优化）；远程扫码/可视化首登流程（体验优化，后续迭代）；MCP Streamable HTTP 多租户服务；单实例多用户形态（信任模型不成立，明确不做）；riskLevel 服务端 RBAC 裁决（按人隔离后优先级下降，后续评估） |
| **前置假设** | 用户规模几十人以内，每容器一个 Chromium 的内存开销可接受；用户能在本地完成目标平台登录并导出登录态，或持有 API token；服务器可运行 Docker；GA 的 TUI/IM 前端在 headless 环境可用（官方文档已确认） |

## 7. 依赖与风险

### 7.1 项目依赖

| 依赖方 | 依赖内容 | 最晚交付时间 | 风险等级 |
|--------|----------|--------------|---------|
| Playwright 官方镜像 | headless Chromium 及系统依赖 | 镜像构建前 | 低 |
| GenericAgent（第三方开源） | headless 运行（TUI/IM 前端）、mykey.py 凭证约定；按官方 installation 文档安装、GA_REF 锁版本 | FEAT-09 前 | 中 |
| IM 渠道 | 每用户的企微/钉钉/TG 机器人凭证 | 用户开通时 | 低 |
| 目标平台 | 对 headless / 数据中心 IP 的风控政策 | 试点验证 | 中 |

### 7.2 风险识别

| 风险ID | 描述 | 影响 | 缓解方案 |
|--------|------|------|---------|
| RISK-01 | 同一服务器出口 IP 上多账号高频访问目标平台，触发风控/封号 | 高 | per-host 限流与退避（platform-command fetch 层统一收口）；小规模试点观察；必要时出口 IP 分离 |
| RISK-02 | storageState 过期频繁，重导入体验差 | 中 | 优先推 token 直连；FEAT-05 过期探测 + 清晰重导入指引 |
| RISK-03 | 提示注入诱导 Agent 滥用容器内系统权限 | 高 | NFR-SEC-03 沙箱配置 + FEAT-09 工具裁剪 + FEAT-08 命令库只读 |
| RISK-04 | GA 工程成熟度（会话持久化、容器化文档）不足 | 中 | 第三方项目按 GA_REF 锁版本，定制限于镜像层不动上游；先 2-3 人试点再放量 |
